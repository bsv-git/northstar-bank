NEXT / BLOCKED

01 · Recover the database baseline

  1. Verify DB_HOST and DB_PORT from .env without exposing secrets; identify the PostgreSQL instance and list its databases.
  2. Inventory all four bank databases and confirm access using the configured application role. Check existing data before creating or restoring anything.
  3. Inspect the four migration dumps, PostgreSQL compatibility and ownership. Back up any current data; select a restore plan before making database changes.
  4. Restore missing bank data or explicitly choose a fresh demo baseline. Do not treat Flyway schema migrations as database creation.

Exit evidence: four intended databases are accessible, baseline data is checked, and the recovery procedure and backup locations are recorded.

PLANNED

02 · Make startup predictable and inexpensive

  1. Add a preflight check for required environment values, PostgreSQL connectivity, database existence, network and port availability.
  2. Start dependencies first and verify each service health endpoint. A gateway UP response alone does not establish full application health.
  3. Measure idle and transfer CPU/RAM. Choose JVM heap and container CPU/memory limits from those measurements; build services sequentially on constrained machines.
  4. Review restart behavior, readiness checks and Kafka persistence. Current Compose uses unless-stopped and has no explicit resource limits, healthchecks or Kafka volume.

Exit evidence: all five services and Kafka are healthy, no restart loop over a 15-minute observation, recorded idle/load measurements, and a documented stop/resume procedure.

PLANNED

03 · Prove the banking workflow

  1. Verify seeded customer/admin login, registration, pre-seeded activation and role restrictions.
  2. Test a transfer using fictional demo funds; reconcile both account balances and ledger entries.
  3. Repeat the same idempotency key and confirm no duplicate posting; reject reuse with changed payment details.
  4. Verify outbox publication, Kafka consumption, notification display and live activity. Test invalid amounts, insufficient funds and dependency outage recovery.

Exit evidence: repeatable smoke/integration checks with expected results and isolated demo fixtures. No automated test source directories were found in the inspected module inventory.

PLANNED

04 · Establish a maintainable development baseline

  1. Initialize version control after excluding credentials, runtime data, build output and backups; establish a reviewed baseline commit.
  2. Add focused regression tests for money movement, authorization, activation and duplicate events.
  3. Document backup/restore drills and service-specific build/restart steps. Review seeding versus activation behavior before changing it.
  4. Update this roadmap after each work session with evidence, changed files, unresolved issues and exactly one next action.

Exit evidence: tracked source, reproducible checks, a tested recovery procedure and a current handoff record.

LATER

05 · Explore pods and future features

  1. After the stable baseline, decide whether Podman pods or Kubernetes serves the learning goal; record that choice.
  2. Define configuration/secrets, persistent storage, resource budgets, readiness and liveness probes before moving services.
  3. Keep PostgreSQL data migration separate and verified. Demonstrate restart recovery in the chosen deployment.
  4. Consider payment prioritization only as a new feature: current recovery orders pending payments by created_at; no priority field is present in the inspected payment request.

Exit evidence: deployment from a clean environment, preserved data and a passing banking smoke suite within an agreed resource budget.
